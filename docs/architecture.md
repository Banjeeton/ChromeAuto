# Архитектура расширения

## Порт AutomationEngine

`AutomationEngine` — граница между прикладной логикой автоматизации и
браузерным драйвером.

```text
core/application -> core/ports/AutomationEngine <- adapters/playwright
```

Core отвечает за порядок шагов, состояния сессий, повторные циклы и правила
остановки. Реализация порта отвечает только за управление вкладкой и выполнение
одного доменного шага. Типы `Browser`, `BrowserContext`, `Page` и другие детали
Playwright CRX не должны пересекать границу порта.

Жизненный цикл одной сессии:

1. `start` привязывает идентификатор сессии к целевой вкладке.
2. `executeStep` выполняется для каждого включенного шага пресета.
3. `complete` освобождает ресурсы после успешного выполнения.
4. `stop` отменяет одну сессию по запросу пользователя или после ошибки.
5. `stopAll` отменяет все активные сессии.

Исключения конкретного драйвера преобразуются в `AutomationEngineError` со
стабильным доменным кодом и контекстом сессии или шага. Исходная ошибка может
быть сохранена в `cause` для журнала, но прикладная логика не должна зависеть от
ее типа.

## Менеджер сессий вкладок

`TabSessionManager` хранит runtime-состояние активных запусков. Для каждой
вкладки разрешена только одна активная сессия, при этом один пресет может
одновременно выполняться в нескольких вкладках.

Менеджер резервирует вкладку до асинхронного вызова `AutomationEngine.start`,
поэтому два параллельных запуска не могут обойти проверку конфликта. Ошибка
запуска снимает резервирование. Успешные `complete`, `stop` и `stopAll` удаляют
runtime-состояние; при ошибке остановки сессия сохраняется для повторной
попытки.

Снимки сессий неизменяемы и не экспортируются вместе с пресетом.

## Привязка автоматизации к сайту

`site-matcher` сопоставляет полный URL вкладки с `SiteBinding` из пресета.
Сравнение выполняется по точному `hostname` и разрешённому протоколу. Порт,
путь, query-параметры и fragment не влияют на результат.

Поддомены не объединяются: `example.com`, `www.example.com` и
`shop.example.com` являются тремя разными сайтами. URL с протоколами кроме
`http` и `https` не поддерживаются.

При выборе автоматизации конфликт нескольких включённых пресетов с одинаковым
hostname считается ошибкой независимо от их настроек протоколов. Отключённые
варианты могут храниться рядом, но активной для hostname бывает только одна
автоматизация.

## Исполнение базовых шагов

`PlaywrightEngine` реализует порт `AutomationEngine`, а преобразование доменных
шагов в вызовы Playwright изолировано в `playwright-step-executor`.

Первая версия исполнителя поддерживает:

- `click` с кнопкой мыши, количеством кликов и fallback-локаторами;
- `input` как мгновенный fill, добавление текста или посимвольный человеческий
  ввод;
- `wait` по времени, состоянию элемента, URL или состоянию загрузки страницы;
- `reload`, включая раннее продолжение при `waitUntil: none`.

Для действий применяется таймаут шага либо общий таймаут автоматизации. После
успешного шага выполняется его собственная либо общая задержка. Ошибки
Playwright преобразуются в `AutomationEngineError` с идентификатором сессии,
вкладки и шага.

## Выполнение custom JavaScript

Шаг `customCode` выполняется Playwright в контексте текущей страницы. Исходный
код поддерживает `await` и получает объект API версии 1:

- `automation.log(value)` сохраняет значение в журнал результата;
- `await automation.sleep(milliseconds)` создаёт управляемую паузу;
- `automation.stop(reason)` останавливает текущий проход.

Успешный шаг возвращает сериализуемое значение и накопленные записи журнала в
`AutomationStepExecutionResult.output`. Ошибка скрипта, превышение таймаута и
запрошенная остановка преобразуются в разные доменные коды.

Custom JavaScript является доверенным пользовательским кодом, а не защитной
песочницей: он имеет доступ к DOM и данным открытой страницы. Таймаут позволяет
движку продолжить обработку ошибки, но уже запущенный асинхронный код страницы
не всегда можно принудительно прервать средствами `page.evaluate`.

## Stop и Stop All

`AutomationRuntimeController` предоставляет background-слою две идемпотентные
команды управления. `Stop` отменяет сессию активной вкладки, а `Stop All` — все
текущие сессии.

Запрос остановки немедленно отменяет `AbortSignal` сессии и переводит её в
`stopping`, после чего Playwright отсоединяется от вкладки. Остановка одной
вкладки не влияет на остальные. При технической ошибке detach сессия остаётся
в `stopping`, поэтому команду можно безопасно повторить.

Background service worker принимает команды `stop`, `stop-all` и `sessions`
через канал `automation/runtime`. Side panel использует этот контракт для
кнопок `Stop current tab` и `Stop All` без прямой зависимости от Playwright или
менеджера сессий.

## Обработка ошибок и журнал шагов

`AutomationRunner` запускает сессию, последовательно выполняет включённые шаги
и завершает её после успешного прохода. Отключённые шаги не передаются движку,
но отмечаются в журнале как `skipped`.

Для каждого обработанного шага журнал содержит:

- идентификатор, порядковый номер, тип и необязательное название шага;
- идентификаторы пресета, сессии и вкладки;
- статус `succeeded`, `skipped`, `failed` или `stopped`;
- время записи и длительность;
- результат шага либо доменный код и текст ошибки.

Первая ошибка прекращает проход, последующие шаги не выполняются, а сессия
останавливается с причиной `error`. Пользовательский Stop и
`automation.stop()` записываются как `stopped`, а не как ошибка. Неизвестные
исключения преобразуются в `AutomationEngineError` с кодом `step-failed` и
контекстом ошибочного шага.

`InMemoryExecutionLog` хранит не более 500 последних записей и поддерживает
фильтрацию и очистку по сессии, пресету или вкладке. Журнал является временным
runtime-состоянием и не экспортируется вместе с пресетом.

## Ручной запуск из side panel

Side panel не выполняет автоматизацию самостоятельно. Он передаёт в background
только `tabId`, а background получает актуальный URL через Chrome Tabs API. Это
не позволяет интерфейсу подменить адрес целевой вкладки.

`ManualRunController` читает пресеты через порт `PresetRepository`, выбирает
единственный включённый preset v1 по точному hostname и разрешённому протоколу,
а затем проверяет run-only правила. Если активного назначения нет, отключённый
вариант используется только для отображения понятного статуса. Лишь после
проверок автоматизация передаётся в `AutomationRunner`.

```text
side panel -> automation/runtime -> ManualRunController
                                      |-> PresetRepository <- Chrome storage
                                      |-> AutomationRunner -> AutomationEngine
```

`ChromePresetRepository` хранит массив portable preset v1 в
`chrome.storage.local` под одним версионированным ключом. При сохранении
hostname приводится к нижнему регистру, а попытка включить два разных пресета
для одного hostname отклоняется. Отключённые альтернативы разрешены. Мутации
сериализуются внутри репозитория, поэтому
параллельные операции одного service worker не перезаписывают результаты друг
друга. Ошибки чтения, записи и повреждённой коллекции имеют отдельные типы.
База данных для этого слоя не используется.

Side panel показывает состояние `ready`, `running` или `unavailable`, разрешает
ручной Run только для валидного включённого пресета, предоставляет Stop и Stop
All и читает журнал шагов активной вкладки через тот же runtime-контракт.

Выбор пресета для Run выполняет background по актуальному URL вкладки, а не по
выделению в списке side panel. Поэтому пользователь не может случайно запустить
пресет другого hostname. Чтение статуса не запускает движок: выполнение
начинается только после ручной команды `run`. При отсутствии назначения кнопка
недоступна, а статус содержит точный hostname и объяснение.

Изменение `chrome.storage.local` обновляет одновременно список пресетов и статус
активной вкладки. `ManualRunController` передаёт сохранённую автоматизацию в уже
существующие `AutomationRunner` и `AutomationEngine`; отдельный исполнитель для
side panel не создаётся. `TabSessionManager` продолжает изолировать такие
запуски по `tabId`, поэтому переключение вкладки не останавливает другую сессию.

## Повторяющиеся циклы

Повторяющийся цикл — runtime-процесс для одной вкладки и одного сохранённого
пресета. Настройка `siteSettings.repeat.enabled` только разрешает повторение и
сама по себе ничего не запускает. Первый проход всегда начинается явной
командой Run из side panel. Импорт, сохранение пресета, открытие сайта и запуск
Chrome не являются командами запуска.

Состояние цикла описывается конечным автоматом:

| Состояние | Значение |
| --- | --- |
| `idle` | Для вкладки нет активного цикла или завершён одиночный проход без повторения. |
| `running` | `AutomationRunner` выполняет текущий проход во вкладке. |
| `waiting` | Предыдущий проход успешен, а следующий запуск ожидает таймера. |
| `stopped` | Цикл остановлен пользователем либо потерял допустимый контекст; таймера нет. |
| `failed` | Проход или планировщик завершился ошибкой; автоматического повтора нет. |

Основные переходы:

```text
idle / stopped / failed -- manual Run --------> running
running -- success + repeat disabled ---------> idle
running -- success + repeat enabled ----------> waiting
waiting -- timer fired -----------------------> running
running -- execution error -------------------> failed
running -- Stop / automation.stop() ----------> stopped
waiting -- Stop / invalid tab or preset ------> stopped
```

Переход из `idle`, `stopped` или `failed` в `running` разрешён только новой
ручной командой. Ошибка шага, ошибка запуска движка или ошибка планировщика
переводит цикл в `failed`, отменяет ожидающий таймер и не выполняет
автоматических повторных попыток. `Stop`, `Stop All` и `automation.stop()`
переводят затронутые циклы в `stopped`.

Если повторение включено, следующий запуск планируется только после успешного
завершения всего прохода. Время следующего запуска вычисляется как время
завершения плюс `intervalMinutes`; длительность автоматизации в интервал не
входит. Пока цикл находится в `running`, новый таймер для него не создаётся,
поэтому проходы одной вкладки не пересекаются. При отключённом повторении
успешный ручной проход возвращает состояние в `idle`.

Перед выполнением отложенного прохода background заново читает актуальный
пресет и проверяет вкладку, точный hostname, протокол, включённое состояние и
настройку repeat. Удаление или отключение пресета, закрытие вкладки либо переход
на другой hostname останавливает цикл без выполнения. Изменённые шаги пресета
применяются со следующего прохода после полной валидации.

Единица изоляции — `tabId`. Один пресет может иметь независимые циклы в
нескольких вкладках с одинаковым hostname: каждый имеет собственное состояние,
текущую сессию и время следующего запуска. Завершение, ошибка, Stop или закрытие
одной вкладки не влияет на остальные. В одной вкладке одновременно разрешён
только один проход и один ожидающий таймер.

Планирование должно учитывать приостановку Manifest V3 service worker. Core
будет зависеть от порта планировщика, а Chrome-адаптер реализует его через
`chrome.alarms`, не через долгоживущий `setTimeout`. Каждый активный цикл имеет
runtime-идентификатор поколения; событие от отменённого или заменённого таймера
игнорируется как устаревшее. Реестр циклов хранится отдельно от
`PresetRepository` и позволяет восстановить состояние после перезапуска service
worker.

Portable preset содержит только декларативные настройки повтора:
`repeat.enabled` и `repeat.intervalMinutes`. В него не входят `tabId`, состояние
цикла, runtime-идентификатор, текущая сессия, время последнего или следующего
запуска, сведения об ошибке и зарегистрированные Chrome alarms. Эти данные не
участвуют в импорте и экспорте и удаляются независимо от portable-пресета.

Предполагаемое разделение компонентов:

```text
side panel -- manual Run --> RepeatCycleController --> AutomationRunner
                                  |                         |
                                  |                         +-> AutomationEngine
                                  |                         +-> ExecutionLog
                                  |
                                  +-> Scheduler port <- Chrome alarms adapter
                                  +-> RepeatCycleStateStore
```

## Создание и редактирование пресетов

Side panel отправляет через `automation/runtime` только редактируемые поля
пресета. `PresetEditorController` в background создаёт UUID и временные метки
для нового пресета. При изменении он сначала читает существующую запись,
сохраняет её `id` и `createdAt`, а `updatedAt` сдвигает вперёд.

```text
side panel editor -> PresetEditorController -> PresetRepository -> Chrome storage
                              |                       |
                       system metadata        full validation
```

Метаданные, точная привязка к hostname, настройки сайта и общие настройки
автоматизации редактируются отдельными полями. Шаги отображаются в порядке
исполнения, поддерживают добавление, удаление и перестановку; полная структура
каждого шага v1 доступна в JSON-редакторе. Репозиторий выполняет JSON Schema и
семантическую валидацию до записи. Ошибка возвращается в форму вместе с путём к
невалидному полю, а редактор остаётся открытым.

Удаление требует отдельного подтверждения в side panel и только после него
передаётся в background. Ошибка чтения или записи оставляет исходный пресет в
списке и отображается рядом с операцией. Дублирование создаёт глубокую копию
редактируемых полей, включая шаги и настройки, после чего открывает её как новый
пресет. Для копии активного пресета hostname очищается намеренно: пользователь
должен назначить другой сайт, чтобы не создать две активные автоматизации для
одного hostname. При сохранении копии background создаёт новый UUID и отдельные
временные метки.

Импорт и экспорт запускаются только явными действиями пользователя в side
panel. Для импорта UI передаёт содержимое выбранного JSON-файла в background,
где оно последовательно проходит разбор JSON, JSON Schema v1, семантическую
валидацию и сохранение через `PresetRepository`. Любая ошибка происходит до
записи либо отклоняет атомарную запись целиком.

Экспорт получает актуальный пресет из репозитория, повторно валидирует его и
возвращает в side panel portable JSON без runtime-состояния. UI создаёт файл
`*.preset.json` только после нажатия `Export JSON`. Автоматизация, точная
привязка к ресурсу и `siteSettings` экспортируются вместе.

## Безопасные операции и диагностика

Удаление и перезапись существующего пресета разделены на подготовку и явное
подтверждение пользователя. При импорте совпадение `id` не приводит к записи:
background возвращает сведения о конфликте и текущий `updatedAt`. Повторный
запрос сохраняет импорт только с этим значением. Если запись успела измениться,
подтверждение считается устаревшим и запрашивается заново.

Валидация, проверка конфликтов и подготовка новой коллекции выполняются до
единственного вызова `chrome.storage.local.set`. Поэтому ошибка на любом этапе
не оставляет частично изменённую коллекцию пресетов.

Ошибки runtime-контракта содержат пользовательское сообщение и отдельную
структурированную диагностику: действие, тип и текст ошибки, стабильный код,
причину, данные валидации и stack trace, когда они доступны. Краткое сообщение с
названием действия отображается рядом с операцией в side panel. Полные детали
можно раскрыть в `Run log`; background дополнительно пишет исходную ошибку в
консоль service worker.
