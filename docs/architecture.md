# Архитектура расширения

UX-структура, навигация, состояния и пользовательские сценарии side panel
зафиксированы отдельно в документе
[UX-архитектура side panel](side-panel-ux.md). Side panel отображает доменное
состояние и отправляет команды, но не переносит правила выполнения, записи или
валидации из core/background в React-компоненты.

## Порт AutomationEngine

`AutomationEngine` — граница между прикладной логикой автоматизации и
браузерным драйвером.

```text
core/application -> core/ports/AutomationEngine <- adapters/playwright
```

Core отвечает за порядок шагов, состояния сессий, повторные циклы и правила
остановки. Реализация порта отвечает только за управление вкладкой и выполнение
одного доменного шага. Типы `Browser`, `BrowserContext`, `Page` и другие детали
Playwright CRX не должны пересекать границу порта.

Жизненный цикл одной сессии:

1. `start` привязывает идентификатор сессии к целевой вкладке.
2. `executeStep` выполняется для каждого включенного шага пресета.
3. `complete` освобождает ресурсы после успешного выполнения.
4. `stop` отменяет одну сессию по запросу пользователя или после ошибки.
5. `stopAll` отменяет все активные сессии.

Исключения конкретного драйвера преобразуются в `AutomationEngineError` со
стабильным доменным кодом и контекстом сессии или шага. Исходная ошибка может
быть сохранена в `cause` для журнала, но прикладная логика не должна зависеть от
ее типа.

## Менеджер сессий вкладок

`TabSessionManager` хранит runtime-состояние активных запусков. Для каждой
вкладки разрешена только одна активная сессия, при этом один пресет может
одновременно выполняться в нескольких вкладках.

Менеджер резервирует вкладку до асинхронного вызова `AutomationEngine.start`,
поэтому два параллельных запуска не могут обойти проверку конфликта. Ошибка
запуска снимает резервирование. Успешные `complete`, `stop` и `stopAll` удаляют
runtime-состояние; при ошибке остановки сессия сохраняется для повторной
попытки.

Снимки сессий неизменяемы и не экспортируются вместе с пресетом.

## Привязка автоматизации к сайту

`site-matcher` сопоставляет полный URL вкладки с `SiteBinding` из пресета.
Сравнение выполняется по точному `hostname` и разрешённому протоколу. Порт,
путь, query-параметры и fragment не влияют на результат.

Поддомены не объединяются: `example.com`, `www.example.com` и
`shop.example.com` являются тремя разными сайтами. URL с протоколами кроме
`http` и `https` не поддерживаются.

При выборе автоматизации конфликт нескольких включённых пресетов с одинаковым
hostname считается ошибкой независимо от их настроек протоколов. Отключённые
варианты могут храниться рядом, но активной для hostname бывает только одна
автоматизация.

## Исполнение базовых шагов

`PlaywrightEngine` реализует порт `AutomationEngine`, а преобразование доменных
шагов в вызовы Playwright изолировано в `playwright-step-executor`.

Первая версия исполнителя поддерживает:

- `click` с кнопкой мыши, количеством кликов и fallback-локаторами;
- `input` как мгновенный fill, добавление текста или посимвольный человеческий
  ввод;
- `wait` по времени, состоянию элемента, URL или состоянию загрузки страницы;
- `reload`, включая раннее продолжение при `waitUntil: none`.

Для действий применяется таймаут шага либо общий таймаут автоматизации. После
успешного шага выполняется его собственная либо общая задержка. Ошибки
Playwright преобразуются в `AutomationEngineError` с идентификатором сессии,
вкладки и шага.

## Архитектура расширенных действий

Этот раздел задаёт целевой контракт для записи, редактирования и выполнения
шагов `select`, `check`, `uncheck` и `pressKey`. Типы уже входят в portable
preset v1 и не требуют новой версии схемы. Пока соответствующие адаптеры не
реализованы, исполнитель обязан отклонять такой шаг как неподдерживаемый, а не
подменять его обычным `click`.

Расширенные действия проходят через существующую цепочку
`AutomationRunner -> AutomationEngine -> PlaywrightStepExecutor`. Core хранит
только типы preset v1 и не зависит от Playwright, DOM или Chrome API. Для цели
используется тот же механизм основного и fallback-локаторов, что и для `click`
и `input`.

### Выполнение действий

- `select` работает только с одиночным `<select>`. Поле `option.by` выбирает
  вариант по `value`, видимому `label` либо нулевому `index`. Отсутствующая
  опция, индекс вне диапазона, несколько совпавших label или неподходящий
  элемент завершают шаг ошибкой. `<select multiple>` в первой версии не
  поддерживается.
- `check` приводит нативный `input[type="checkbox"]` или
  `input[type="radio"]` в отмеченное состояние. Уже отмеченный элемент
  считается успешным результатом без дополнительного пользовательского
  события.
- `uncheck` приводит нативный checkbox в неотмеченное состояние и также
  идемпотентен. `uncheck` для radio и оба действия для элемента, который нельзя
  проверить через стандартную checked-семантику, завершаются ошибкой.
- `pressKey` с `target` сначала находит и фокусирует элемент, затем отправляет
  клавишу этому элементу. Без `target` клавиша отправляется текущему
  `document.activeElement`; исполнитель не ищет элемент и не меняет фокус
  автоматически. Если отдельный элемент не сфокусирован, событие получает
  документ страницы, что позволяет воспроизводить глобальные shortcuts.

Нативные checkbox и radio записываются по изменению состояния, а не как
обычный `click`. Поэтому один жест пользователя создаёт ровно один `check` или
`uncheck`. Для radio записывается только `check` вновь выбранного элемента:
автоматическое снятие состояния с другого radio той же группы не создаёт
`uncheck`. Кастомные элементы с ARIA-ролями `checkbox`, `radio` или `switch`
пока остаются обычными `click`, поскольку их модель состояния определяется
кодом сайта.

### Запись select и специальных клавиш

Content script получает доверенное событие `change` у `<select>` и не создаёт
отдельный `click` при открытии списка. Для выбранной опции стратегия
формируется в следующем порядке:

1. уникальный непустой `value`;
2. уникальный видимый `label`;
3. `selectedIndex` как последний fallback.

События `input` и `click`, сопровождающие то же изменение `<select>`,
подавляются. Изменение `<select multiple>` пропускается с диагностической
записью, пока portable-модель не научится хранить несколько вариантов.

Recorder создаёт `pressKey` только для ограниченного набора специальных клавиш:

- `Enter`, `Escape` и `Tab`;
- `ArrowUp`, `ArrowDown`, `ArrowLeft`, `ArrowRight`, `Home`, `End`, `PageUp` и
  `PageDown`;
- `Insert`, `Delete`, `Backspace` и `Space`;
- `F1`-`F12`;
- комбинации перечисленных клавиш с `Control`, `Alt`, `Shift` или `Meta`.

Имена клавиш и модификаторов сохраняются в каноническом Playwright-формате.
Одиночные клавиши-модификаторы и обычные печатные символы не создают
`pressKey`. В текстовом поле печатные символы, `Space`, `Backspace`, `Delete` и
клавиши перемещения каретки поглощаются потоком `input`: последовательный ввод
остаётся одним шагом `input` с итоговым значением. В текстовом поле отдельно
записываются только `Enter`, `Escape`, `Tab`, функциональные клавиши и их
комбинации с модификаторами. Перед любым отдельным действием отложенный input
финализируется, чтобы порядок шагов совпадал с действиями пользователя.

`pressKey`, записанный на конкретном интерактивном элементе, получает его
локатор. Глобальная клавиатурная команда, для которой исходная цель не является
стабильной или значимой, сохраняется без `target` и при воспроизведении зависит
от фокуса, установленного предыдущими шагами.

### Таймауты, задержки и ошибки

Для каждого расширенного действия действует `step.timeoutMs`, а при его
отсутствии — `defaults.timeoutMs`. Таймаут охватывает поиск по основному и
fallback-локаторам, проверку применимости и само действие. У `pressKey` без
локатора таймаут применяется к общему дедлайну шага и проверке возможности
отправить клавишу, но не запускает ожидание появления элемента.

После любого успешного действия, включая идемпотентный `check` или `uncheck`,
применяется `step.delayAfterMs` либо `defaults.delayAfterMs`. После ошибки,
остановки или пропуска отключённого шага задержка не выполняется.

Ошибки адаптера нормализуются на границе `AutomationEngine`:

- истечение дедлайна даёт `step-timeout`;
- отсутствующий target, неподходящий тип элемента, отсутствующая option,
  неоднозначный label или недопустимая клавиша дают `step-failed` с причиной
  действия;
- ошибка содержит `sessionId`, `tabId`, `stepId` и `stepIndex`, а техническая
  причина остаётся доступна в журнале.

Первая ошибка расширенного действия останавливает текущий проход. Если проход
является частью повторяющегося цикла, новый таймер не назначается.

### События Recorder и редактирование

Внутренний `RecorderEventV1` расширяется событиями `select`, `check`, `uncheck`
и `pressKey`. Их payload хранит только данные захваченного действия: стратегию
option, итоговое checked-состояние либо каноническую клавишу. Служебные поля
`eventId`, `sessionId`, `tabId`, `documentId`, URL, timestamp и признаки
источника остаются runtime-данными в `chrome.storage.session`.

`RecordedStepMapper` преобразует принятые события в одноимённые шаги preset v1
и удаляет все runtime-поля. Редактор работает уже с portable-шагами: для
`select` редактируются target, способ и значение option; для `check` и
`uncheck` — target; для `pressKey` — key и необязательный target. Перед
сохранением черновика, сохранением preset и запуском выполняются структурная и
семантическая валидации.

Внутренние события Recorder не входят в импорт, экспорт и JSON preset v1. В
portable-файл попадают только поля соответствующего `AutomationStep`, поэтому
запись одного и того же действия вручную и через Recorder создаёт одинаковый
контракт выполнения.

## Выполнение custom JavaScript

Шаг `customCode` выполняется Playwright в контексте текущей страницы. Исходный
код поддерживает `await` и получает объект API версии 1:

- `automation.log(value)` сохраняет значение в журнал результата;
- `await automation.sleep(milliseconds)` создаёт управляемую паузу;
- `automation.stop(reason)` останавливает текущий проход.

Успешный шаг возвращает сериализуемое значение и накопленные записи журнала в
`AutomationStepExecutionResult.output`. Ошибка скрипта, превышение таймаута и
запрошенная остановка преобразуются в разные доменные коды.

Custom JavaScript является доверенным пользовательским кодом, а не защитной
песочницей: он имеет доступ к DOM и данным открытой страницы. Таймаут позволяет
движку продолжить обработку ошибки, но уже запущенный асинхронный код страницы
не всегда можно принудительно прервать средствами `page.evaluate`.

## Stop и Stop All

`AutomationRuntimeController` предоставляет background-слою две идемпотентные
команды управления. `Stop` отменяет сессию активной вкладки, а `Stop All` — все
текущие сессии.

Запрос остановки немедленно отменяет `AbortSignal` сессии и переводит её в
`stopping`, после чего Playwright отсоединяется от вкладки. Остановка одной
вкладки не влияет на остальные. При технической ошибке detach сессия остаётся
в `stopping`, поэтому команду можно безопасно повторить.

Background service worker принимает команды `stop`, `stop-all` и `sessions`
через канал `automation/runtime`. Side panel использует этот контракт для
кнопок `Stop current tab` и `Stop All` без прямой зависимости от Playwright или
менеджера сессий.

## Обработка ошибок и журнал шагов

`AutomationRunner` запускает сессию, последовательно выполняет включённые шаги
и завершает её после успешного прохода. Отключённые шаги не передаются движку,
но отмечаются в журнале как `skipped`.

Для каждого обработанного шага журнал содержит:

- идентификатор, порядковый номер, тип и необязательное название шага;
- идентификаторы пресета, сессии и вкладки;
- статус `succeeded`, `skipped`, `failed` или `stopped`;
- время записи и длительность;
- результат шага либо доменный код и текст ошибки.

Первая ошибка прекращает проход, последующие шаги не выполняются, а сессия
останавливается с причиной `error`. Пользовательский Stop и
`automation.stop()` записываются как `stopped`, а не как ошибка. Неизвестные
исключения преобразуются в `AutomationEngineError` с кодом `step-failed` и
контекстом ошибочного шага.

`InMemoryExecutionLog` хранит не более 500 последних записей и поддерживает
фильтрацию и очистку по сессии, пресету или вкладке. Журнал является временным
runtime-состоянием и не экспортируется вместе с пресетом.

## Ручной запуск из side panel

Side panel не выполняет автоматизацию самостоятельно. Он передаёт в background
только `tabId`, а background получает актуальный URL через Chrome Tabs API. Это
не позволяет интерфейсу подменить адрес целевой вкладки.

`ManualRunController` читает пресеты через порт `PresetRepository`, выбирает
единственный включённый preset v1 по точному hostname и разрешённому протоколу,
а затем проверяет run-only правила. Если активного назначения нет, отключённый
вариант используется только для отображения понятного статуса. Лишь после
проверок автоматизация передаётся в `AutomationRunner`.

```text
side panel -> automation/runtime -> ManualRunController
                                      |-> PresetRepository <- Chrome storage
                                      |-> AutomationRunner -> AutomationEngine
```

`ChromePresetRepository` хранит массив portable preset v1 в
`chrome.storage.local` под одним версионированным ключом. При сохранении
hostname приводится к нижнему регистру, а попытка включить два разных пресета
для одного hostname отклоняется. Отключённые альтернативы разрешены. Мутации
сериализуются внутри репозитория, поэтому
параллельные операции одного service worker не перезаписывают результаты друг
друга. Ошибки чтения, записи и повреждённой коллекции имеют отдельные типы.
База данных для этого слоя не используется.

Side panel показывает состояние `ready`, `running` или `unavailable`, разрешает
ручной Run только для валидного включённого пресета, предоставляет Stop и Stop
All и читает журнал шагов активной вкладки через тот же runtime-контракт.

Выбор пресета для Run выполняет background по актуальному URL вкладки, а не по
выделению в списке side panel. Поэтому пользователь не может случайно запустить
пресет другого hostname. Чтение статуса не запускает движок: выполнение
начинается только после ручной команды `run`. При отсутствии назначения кнопка
недоступна, а статус содержит точный hostname и объяснение.

Изменение `chrome.storage.local` обновляет одновременно список пресетов и статус
активной вкладки. `ManualRunController` передаёт сохранённую автоматизацию в уже
существующие `AutomationRunner` и `AutomationEngine`; отдельный исполнитель для
side panel не создаётся. `TabSessionManager` продолжает изолировать такие
запуски по `tabId`, поэтому переключение вкладки не останавливает другую сессию.

## Повторяющиеся циклы

Повторяющийся цикл — runtime-процесс для одной вкладки и одного сохранённого
пресета. Настройка `siteSettings.repeat.enabled` только разрешает повторение и
сама по себе ничего не запускает. Первый проход всегда начинается явной
командой Run из side panel. Импорт, сохранение пресета, открытие сайта и запуск
Chrome не являются командами запуска.

Состояние цикла описывается конечным автоматом:

| Состояние | Значение |
| --- | --- |
| `idle` | Для вкладки нет активного цикла или завершён одиночный проход без повторения. |
| `running` | `AutomationRunner` выполняет текущий проход во вкладке. |
| `waiting` | Предыдущий проход успешен, а следующий запуск ожидает таймера. |
| `stopped` | Цикл остановлен пользователем либо потерял допустимый контекст; таймера нет. |
| `failed` | Проход или планировщик завершился ошибкой; автоматического повтора нет. |

Основные переходы:

```text
idle / stopped / failed -- manual Run --------> running
running -- success + repeat disabled ---------> idle
running -- success + repeat enabled ----------> waiting
waiting -- timer fired -----------------------> running
running -- execution error -------------------> failed
running -- Stop / automation.stop() ----------> stopped
waiting -- Stop / invalid tab or preset ------> stopped
```

Переход из `idle`, `stopped` или `failed` в `running` разрешён только новой
ручной командой. Ошибка шага, ошибка запуска движка или ошибка планировщика
переводит цикл в `failed`, отменяет ожидающий таймер и не выполняет
автоматических повторных попыток. `Stop`, `Stop All` и `automation.stop()`
переводят затронутые циклы в `stopped`.

Если повторение включено, следующий запуск планируется только после успешного
завершения всего прохода. Время следующего запуска вычисляется как время
завершения плюс `intervalMinutes`; длительность автоматизации в интервал не
входит. Пока цикл находится в `running`, новый таймер для него не создаётся,
поэтому проходы одной вкладки не пересекаются. При отключённом повторении
успешный ручной проход возвращает состояние в `idle`.

Перед выполнением отложенного прохода background заново читает актуальный
пресет и проверяет вкладку, точный hostname, протокол, включённое состояние и
настройку repeat. Удаление или отключение пресета, закрытие вкладки либо переход
на другой hostname останавливает цикл без выполнения. Изменённые шаги пресета
применяются со следующего прохода после полной валидации.

Дополнительно background подписан на `chrome.tabs.onUpdated` и
`chrome.tabs.onRemoved`. Смена URL немедленно отменяет таймер и текущую сессию,
если точный hostname или протокол больше не соответствует preset. Закрытие
вкладки удаляет только runtime-состояние и alarm её `tabId`; циклы других
вкладок не изменяются. Та же проверка повторяется непосредственно в
`chrome.alarms.onAlarm`, чтобы навигация или закрытие вкладки не могли пройти
между событием Chrome и автоматическим запуском.

Единица изоляции — `tabId`. Один пресет может иметь независимые циклы в
нескольких вкладках с одинаковым hostname: каждый имеет собственное состояние,
текущую сессию и время следующего запуска. Завершение, ошибка, Stop или закрытие
одной вкладки не влияет на остальные. В одной вкладке одновременно разрешён
только один проход и один ожидающий таймер.

Планирование должно учитывать приостановку Manifest V3 service worker. Core
зависит от порта `CycleScheduler`, а адаптер `ChromeAlarmScheduler` реализует
его через одноразовые `chrome.alarms`, не через долгоживущий `setTimeout`.
Каждый alarm однозначно кодирует пару `tabId` и `presetId`. Следующий alarm
создаётся прикладным слоем только после успешного прохода. Каждый активный цикл
имеет runtime-идентификатор поколения; событие от отменённого или заменённого
таймера игнорируется как устаревшее. `ChromeRepeatCycleRegistry` хранит реестр
циклов в `chrome.storage.session` под отдельным версионированным ключом. Он не
использует `PresetRepository` и позволяет восстановить состояние после
перезапуска service worker в рамках текущей сессии браузера. Записи разных
вкладок сериализуются без потери обновлений; повреждённые записи и состояния,
которые больше не соответствуют допустимой паре вкладки и пресета, удаляются.

`RepeatCycleController` используется как ручным запуском, так и обработчиком
`chrome.alarms.onAlarm`. Перед отложенным проходом обработчик заново читает
пресет по `presetId`, а контроллер принимает событие только для состояния
`waiting` с совпадающим `nextRunAt`. После успешного `AutomationRunner.run`
контроллер создаёт следующий одноразовый alarm; после ошибки сохраняет
`failed` или `stopped` и не планирует продолжение.

`AutomationRuntimeController` объединяет остановку текущих `RunSession` и
повторяющихся циклов. `Stop` инвалидирует поколение выбранного `tabId`, отменяет
его alarm и прерывает активную сессию; `Stop All` делает то же для всех вкладок.
Перед созданием alarm и после каждой асинхронной записи контроллер повторно
проверяет поколение цикла. Поэтому завершившийся одновременно со Stop проход не
может вернуть состояние в `waiting` или создать будущий повтор. Повторная
команда Stop для уже остановленного цикла является безопасной пустой операцией.

Manual status включает состояние `waiting`, чтобы кнопка Stop оставалась
доступной между проходами. После Stop и Stop All side panel повторно запрашивает
status и список сессий, поэтому состояние интерфейса обновляется сразу после
подтверждённой остановки background.

`RepeatCycleStatusController` объединяет runtime-реестр с актуальными
пресетами и отдаёт side panel только активные состояния `Running` и `Waiting`.
Для каждого цикла показываются связанный `tabId`, имя пресета, текущий интервал
и `nextRunAt`. Side panel следит за изменениями отдельного ключа
`chrome.storage.session`, поэтому переходы между Running и Waiting появляются
без ручного обновления.

События планировщика записываются через отдельный порт `RepeatCycleLog`, не
смешивая их с результатами отдельных шагов `ExecutionLog`. Журнал фиксирует
начало и успешное завершение прохода, назначение следующего alarm, Stop и
Stop All, ошибку с `stepId`/номером шага, закрытие вкладки и смену hostname или
протокола. Lifecycle-журнал общий для вкладок, поэтому причина закрытия вкладки
остаётся видимой после переключения Chrome на другую активную вкладку.

`RepeatCycleRecoveryController` запускает reconciliation при каждом создании
service worker. Он сопоставляет записи `chrome.alarms`, runtime-реестр,
актуальные preset v1 и URL вкладок. Сохраняются только таймеры в состоянии
`waiting` с точным `nextRunAt`, валидным включённым preset и совпадающим
hostname/protocol. Осиротевшие alarms и runtime-записи удаляются. Обработчик
alarm повторяет эту проверку перед запуском, поэтому повторная доставка одного
события не создаёт второй проход цикла.

Если валидное состояние `waiting` сохранилось, но одноразовый alarm отсутствует,
reconciliation создаёт его заново с тем же `nextRunAt`. Это покрывает момент,
когда Chrome уже извлёк alarm для доставки во время запуска service worker:
повторное событие с прежним временем будет проигнорировано после перехода
цикла в новое состояние.

Portable preset содержит только декларативные настройки повтора:
`repeat.enabled` и `repeat.intervalMinutes`. В него не входят `tabId`, состояние
цикла, runtime-идентификатор, текущая сессия, время последнего или следующего
запуска, сведения об ошибке и зарегистрированные Chrome alarms. Эти данные не
участвуют в импорте и экспорте и удаляются независимо от portable-пресета.

Предполагаемое разделение компонентов:

```text
side panel -- manual Run --> RepeatCycleController --> AutomationRunner
                                  |                         |
                                  |                         +-> AutomationEngine
                                  |                         +-> ExecutionLog
                                  |
                                  +-> CycleScheduler <- ChromeAlarmScheduler
                                  +-> RepeatCycleStateStore
```

## Создание и редактирование пресетов

Side panel отправляет через `automation/runtime` только редактируемые поля
пресета. `PresetEditorController` в background создаёт UUID и временные метки
для нового пресета. При изменении он сначала читает существующую запись,
сохраняет её `id` и `createdAt`, а `updatedAt` сдвигает вперёд.

```text
side panel editor -> PresetEditorController -> PresetRepository -> Chrome storage
                              |                       |
                       system metadata        full validation
```

Метаданные, точная привязка к hostname, настройки сайта и общие настройки
автоматизации редактируются отдельными полями. Шаги отображаются в порядке
исполнения, поддерживают добавление, удаление и перестановку; полная структура
каждого шага v1 доступна в JSON-редакторе. Репозиторий выполняет JSON Schema и
семантическую валидацию до записи. Ошибка возвращается в форму вместе с путём к
невалидному полю, а редактор остаётся открытым.

Удаление требует отдельного подтверждения в side panel и только после него
передаётся в background. Ошибка чтения или записи оставляет исходный пресет в
списке и отображается рядом с операцией. Дублирование создаёт глубокую копию
редактируемых полей, включая шаги и настройки, после чего открывает её как новый
пресет. Для копии активного пресета hostname очищается намеренно: пользователь
должен назначить другой сайт, чтобы не создать две активные автоматизации для
одного hostname. При сохранении копии background создаёт новый UUID и отдельные
временные метки.

Импорт и экспорт запускаются только явными действиями пользователя в side
panel. Для импорта UI передаёт содержимое выбранного JSON-файла в background,
где оно последовательно проходит разбор JSON, JSON Schema v1, семантическую
валидацию и сохранение через `PresetRepository`. Любая ошибка происходит до
записи либо отклоняет атомарную запись целиком.

Экспорт получает актуальный пресет из репозитория, повторно валидирует его и
возвращает в side panel portable JSON без runtime-состояния. UI создаёт файл
`*.preset.json` только после нажатия `Export JSON`. Автоматизация, точная
привязка к ресурсу и `siteSettings` экспортируются вместе.

## Automation Recorder

Automation Recorder записывает действия пользователя только после явной
команды из side panel и формирует редактируемый черновик шагов preset v1.
Единица изоляции рекордера — `tabId`: разные вкладки могут иметь независимые
сессии записи, но в одной вкладке одновременно разрешена только одна сессия.

Компоненты разделены следующим образом:

```text
side panel -- commands/status --> background RecorderController
                                      |       |             |
                                      |       |             +-> PresetEditorController
                                      |       +-> RecorderSessionRegistry
                                      |
content script -- DOM events ---------+
       |
       +-> LocatorGenerator -> RecorderEventV1 -> RecordedStepMapper
```

- **content script** устанавливает и удаляет DOM-обработчики по команде
  background, строит кандидаты локаторов и передаёт только внутренние события
  записи. Он не хранит preset, не сохраняет черновик и не управляет состоянием
  сессии;
- **background** является единственным владельцем состояния, порядка событий и
  черновика. `RecorderController` проверяет контекст вкладки, устраняет
  дубликаты, преобразует события в шаги и реагирует на жизненный цикл вкладки и
  документа;
- **side panel** отправляет ручные команды Record, Stop и Discard, показывает
  актуальное состояние и редактируемый черновик. UI не подключает обработчики
  к странице напрямую и не записывает preset в `chrome.storage.local`;
- **PresetEditorController** принимает только финализированный черновик,
  создаёт системные метаданные и сохраняет результат через существующий
  `PresetRepository` после полной валидации.

Core зависит от порта `Recorder`, а Chrome-адаптеры инкапсулируют messaging,
DOM content script и события навигации. Типы DOM, `chrome.tabs` и
`chrome.webNavigation` не пересекают границу core.

### Состояния сессии записи

Сессия имеет одно из пяти состояний:

| Состояние | Значение |
| --- | --- |
| `idle` | Для вкладки нет активной записи или сохранённого черновика. |
| `recording` | Content script принимает действия, background добавляет их в черновик. |
| `stopping` | Новые события больше не принимаются, выполняется отключение content script и финализация черновика. |
| `stopped` | Запись завершена, черновик доступен для просмотра, редактирования, сохранения или удаления. |
| `failed` | Запись прекращена технической ошибкой; причина и уже собранный черновик сохранены. |

Допустимые переходы:

```text
idle ---------------- manual Record ----------------> recording
stopped / failed ---- manual Record + confirmation -> recording
recording ------------ manual Stop -----------------> stopping -> stopped
recording ------------ hostname/protocol changed --> stopping -> stopped
recording ------------ tab closed -----------------> stopping -> stopped
recording / stopping - technical error ------------> failed
stopped / failed ----- Discard ---------------------> idle
stopped -------------- successful Save ------------> idle
```

Record всегда является ручной командой. Новая запись из `stopped` или `failed`
не перезаписывает существующий черновик без явного подтверждения. В состоянии
`stopping` события отвергаются, поэтому события, пришедшие одновременно со Stop,
не могут изменить уже финализированный черновик. Повторные Stop и Discard
идемпотентны.

### Внутренние события записи

Manifest подключает классический `content-script-loader.js`, который загружает
собранный модуль Recorder через `dynamic import`. Сам модуль и его chunks
объявлены в `web_accessible_resources`. Это необходимо, потому что статические
ES-module imports не поддерживаются непосредственно в `content_scripts`.

Если вкладка была открыта до установки или Reload расширения, background при
ошибке `Receiving end does not exist` внедряет loader через `chrome.scripting`
и повторяет команду запуска ограниченное число раз. Для остальных ошибок
автоматическое внедрение не выполняется, чтобы не скрывать реальную ошибку
content script и не создавать дубликаты обработчиков.

Content script передаёт версионированный `RecorderEventV1`:

```ts
interface RecorderEventV1 {
  version: 1;
  eventId: string;
  sessionId: string;
  tabId: number;
  documentId: string;
  occurredAt: string;
  url: string;
  kind:
    | "click"
    | "input"
    | "select"
    | "check"
    | "uncheck"
    | "pressKey"
    | "reload"
    | "pageReady";
  target?: RecorderTargetCandidate;
  payload: Record<string, unknown>;
}
```

`eventId` обеспечивает идемпотентную доставку, `sessionId` отбрасывает события
предыдущей записи, а `documentId` отделяет документы до и после навигации.
Окончательный порядковый номер назначает background в момент атомарного
добавления события. В payload клика входят кнопка, количество кликов и
модификаторы; ввод содержит итоговое значение и тип элемента; select содержит
стратегию выбранной option; check и uncheck содержат тип нативного контрола и
итоговое состояние; pressKey содержит каноническое имя клавиши; reload содержит
тип перехода и ожидаемое состояние загрузки. Поля паролей и другие явно
неподдерживаемые значения не передаются.

Принимаются только события активной сессии с совпадающими `tabId`, `sessionId`,
hostname и протоколом. Дубликат `eventId`, запоздавшее событие старого документа
или событие после перехода в `stopping` безопасно игнорируется и не создаёт
новый шаг.

### Преобразование в preset v1

Внутренний поток событий не является частью preset. `RecordedStepMapper`
последовательно преобразует принятые события:

- `click` создаёт включённый шаг `click` с основной целью и ограниченным
  набором fallback-локаторов;
- последовательные `input` одного элемента объединяются, а итоговое значение
  создаёт один включённый шаг `input` с `clearFirst: true`;
- `select` создаёт один шаг `select` с выбранной стратегией option;
- изменение нативного checkbox создаёт `check` или `uncheck`, а выбор radio —
  только `check`; связанный click повторно не записывается;
- поддерживаемая специальная клавиша создаёт `pressKey` с локатором значимой
  цели либо без него для команды, зависящей от текущего фокуса;
- `reload` создаёт один шаг `reload`; повторные уведомления Chrome и нового
  content script устраняются по идентификаторам документа и навигации;
- `pageReady` после действия, которое сменило документ на том же hostname,
  может создать `wait` с условием `pageLoad`, если ожидание не покрыто шагом
  `reload`;
- неподдерживаемое действие не добавляется в preset, но фиксируется в журнале
  рекордера с понятной причиной.

Каждый созданный шаг получает новый уникальный `id`, `enabled: true` и
стабильный локатор, соответствующий схеме preset v1. Сначала выбираются
доступные `testId`, role, label или placeholder, затем устойчивый CSS как
fallback. Черновик сохраняет порядок, назначенный background. Перед передачей
в редактор структура шагов проходит JSON Schema и семантическую валидацию.

`wait` и `customCode`, которые нельзя однозначно вывести из действий
пользователя, добавляются вручную в редакторе после Stop.

### Reload и жизненный цикл вкладки

Runtime-сессия хранится в background, поэтому уничтожение content script при
reload не завершает запись. Адаптер навигации фиксирует reload один раз,
переводит сессию на новый `documentId` и после `pageReady` повторно включает
content script. Пока новый документ не зарегистрирован, его DOM-события не
принимаются. Приостановка Manifest V3 service worker также не завершает запись:
сессия восстанавливается из `RecorderSessionRegistry`, после чего background
проверяет вкладку и повторно синхронизирует content script.

Переход по другому пути или query в пределах исходного hostname и протокола не
создаёт новую сессию. Переход на другой hostname либо смена `http`/`https`
немедленно переводит запись через `stopping` в `stopped` с причиной
`tab-context-changed`; события нового документа не записываются. Уже собранный
черновик сохраняется для ручного редактирования.

Закрытие вкладки завершает только связанную с ней запись, удаляет DOM-канал и
сохраняет финализированный черновик с причиной `tab-closed`. Записи остальных
вкладок не изменяются. Черновик существует до Save или Discard либо до конца
текущей сессии браузера.

### Взаимодействие с AutomationEngine

Recorder не вызывает `AutomationEngine` и не использует Playwright для захвата
действий. Он наблюдает только за действиями пользователя через content script.
После сохранения полученный preset выполняется обычным путём через
`AutomationRunner` и `AutomationEngine`.

Запись и выполнение взаимоисключаются в пределах одной вкладки:

- Record отклоняется, если для `tabId` существует активная RunSession или
  повторяющийся цикл в состоянии `running` либо `waiting`;
- ручной Run и автоматический повтор отклоняются, если Recorder находится в
  `recording` или `stopping`;
- запись и выполнение в других вкладках продолжаются независимо.

Это исключает попадание действий Playwright в записываемый сценарий и не
позволяет двум владельцам одновременно управлять одной страницей.

### Отделение runtime-состояния

`RecorderSessionRegistry` использует отдельный версионированный ключ в
`chrome.storage.session`. В нём могут находиться `tabId`, `sessionId`,
`documentId`, состояние, исходный URL, причина остановки, внутренние события и
редактируемый черновик. Эти данные не читаются `PresetRepository` и не
участвуют в импорте или экспорте.

Portable preset v1 получает только декларативные поля, уже описанные схемой:
метаданные, `site`, `automation` и `siteSettings`. В него не попадают состояние
рекордера, идентификаторы вкладки и документа, внутренние timestamps, история
событий, причина остановки или временные кандидаты локаторов. При Save
background создаёт чистый объект preset v1, полностью валидирует его и только
после этого передаёт в существующий `PresetRepository`.

### Журнал и ошибки рекордера

Рекордер пишет отдельные типизированные записи в `RecorderLog`. Журнал фиксирует
успешный старт, каждое принятое действие, ручную остановку, смену hostname,
закрытие вкладки и ошибки захвата либо message-канала. Запись содержит действие,
понятное пользовательское сообщение, `tabId`, `sessionId` и, когда применимо,
идентификатор и тип внутреннего события. Для ошибок отдельно сохраняются имя,
стабильный код Recorder, исходная причина и stack trace.

Content script отправляет ошибки захвата отдельным типизированным diagnostic-
сообщением. Ошибка обработки одного события журналируется и возвращается
отправителю, но существующий `RecorderSessionRecord` не перезаписывается: уже
накопленные события и шаги остаются доступными для Stop и редактирования.
`tab-context-changed` и `tab-closed` являются разными событиями журнала и
разными причинами остановки. Записи доступны в `Run log` side panel; блок
`Technical details` раскрывает диагностические поля.

`RecorderLog` относится только к runtime и не читается `PresetRepository`,
поэтому его записи никогда не входят в portable preset v1 и экспортируемый JSON.

## Безопасные операции и диагностика

Удаление и перезапись существующего пресета разделены на подготовку и явное
подтверждение пользователя. При импорте совпадение `id` не приводит к записи:
background возвращает сведения о конфликте и текущий `updatedAt`. Повторный
запрос сохраняет импорт только с этим значением. Если запись успела измениться,
подтверждение считается устаревшим и запрашивается заново.

Валидация, проверка конфликтов и подготовка новой коллекции выполняются до
единственного вызова `chrome.storage.local.set`. Поэтому ошибка на любом этапе
не оставляет частично изменённую коллекцию пресетов.

Ошибки runtime-контракта содержат пользовательское сообщение и отдельную
структурированную диагностику: действие, тип и текст ошибки, стабильный код,
причину, данные валидации и stack trace, когда они доступны. Краткое сообщение с
названием действия отображается рядом с операцией в side panel. Полные детали
можно раскрыть в `Run log`; background дополнительно пишет исходную ошибку в
консоль service worker.
